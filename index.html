Virtualization & Orchestration Stack

This environment uses a mixed platform strategy so each workload runs on the right abstraction level: containers for portability, orchestration for multi-service systems, and VMs for full OS isolation.

Docker container runtime

  • Supports fast deployment of web apps, APIs, tools, and utility services.
  • How: Images package dependencies once, then run consistently across hosts.
  • Why: Speeds iteration, simplifies updates, and reduces environment drift.
  • Best fit: Stateless apps, service wrappers, scheduled workers, and edge utilities.

Kubernetes (k3d) orchestration layer

  • Supports multi-service systems with scaling, restart logic, and service routing.
  • How: Declarative manifests define desired state; controller loops keep workloads healthy.
  • Why: Better reliability and lifecycle control for complex project stacks.
  • Best fit: Story systems, API groups, and services needing rolling updates and ingress.

Hyper-V windows virtualization

  • Supports full guest operating systems on the Windows workstation.
  • How: Native hypervisor integration provides virtual switching, isolation, and snapshots/checkpoints.
  • Why: Safe testing for OS-level changes without risking the primary host setup.
  • Best fit: Windows-native lab scenarios, network simulation, and system behavior testing.

VMware Workstation cross-os VM lab

  • Supports parallel Linux VM environments for toolchains and integration tests.
  • How: Snapshot-driven workflows enable quick rollback and repeatable test states.
  • Why: Great for controlled experiments, compatibility validation, and sandboxing.
  • Best fit: Multi-node simulations, distro comparisons, and pre-deployment verification.

Network Stack

The network layer is built around private service discovery, encrypted cross-host transport, and clear role boundaries between local hardware and cloud nodes.

BIND9 Implementation private DNS authority

  • BIND9 serves as the authoritative resolver for my private lab zone.
  • How: Internal records map service names to private endpoints for predictable routing.
  • Why: Stable hostnames let projects move between nodes without rewriting app configs.
  • Result: Cleaner operations, easier service migrations, and less hardcoded addressing.

NetBird VPN Usage wireguard mesh overlay

  • NetBird provides encrypted peer-to-peer connectivity between home lab nodes and VPS hosts.
  • How: A mesh overlay makes each machine reachable as if on one secure private fabric.
  • Why: Services can communicate directly without exposing internal APIs to the public internet.
  • Result: Safe cross-site traffic for orchestration, data sync, and service-to-service requests.

Hardware Interaction Model right workload, right node

  • Betelgeuse handles heavy compute, model inference, and orchestration.
  • UYScuti focuses on development, game builds, and workstation-class experiments.
  • hera-pi runs lightweight utility services and always-on support tasks.
  • Cloud hosts provide public entry points while private internals stay on the mesh.

How It Supports Projects design rationale

  • Named DNS services + mesh routing make multi-node projects composable and maintainable.
  • Container and VM platforms can consume the same internal network conventions.
  • Public and private planes stay separated: internet-facing UX, private backend control paths.
  • This architecture supports AI apps, story systems, monitoring tools, and game services together.

AI & Story

Story Universe Ecosystem distributed narrative system

The Story Universe is a distributed, AI-driven narrative world that runs continuously across my homelab. The Chronicle Keeper (hera-pi, Raspberry Pi 5) holds the canonical world state — characters, factions, locations, and events in SQLite — and broadcasts a world clock via ZeroMQ. The Narrative Engine (Betelgeuse) subscribes to those ticks and generates story arcs and events through the Halfax AI API, targeting the Dark Champion LLM. The World Browser (served from my Guy Rocky Linux host) presents the live chronicle as a public web dashboard reading from both the Chronicle Keeper REST API and the arcs API.

Connecting them is MemPalace — a ChromaDB-backed semantic memory framework co-created by actress Milla Jovovich and engineer Ben Sigman, designed to give AI models long-term memory that mimics human spatial recall. Every accepted story event and arc update is written to MemPalace in real time by the Narrative Engine. Before each LLM generation call, the engine searches MemPalace for relevant past events and injects them as narrative context, so the LLM builds on what happened before rather than generating in isolation. The Halfax AI API also exposes MemPalace search and purge endpoints, allowing any system to query or reset story memory. When a story is archived, MemPalace is automatically purged so the next story starts with a clean slate.

Resilience: All services auto-start under systemd with infinite retry. A HealthMonitor probes the Chronicle Keeper and LLM endpoints every tick — if either is unhealthy, the engine pauses instead of fabricating events, and resumes silently when dependencies recover. There is no template fallback: when the LLM is down, the universe simply waits. Chronicle Keeper REST calls use automatic retry with back-off for transient blips.

Prose quality pipeline: Every generated event passes through a post-generation regex filter that rejects atmospheric-formula openings (“Dawn sunlight filters through the windows…”), tension-family clichés, and time-of-day contradictions. Rejected attempts feed back into the next retry as real-time negative examples, letting the LLM escape its trained reflexes. The engine retries up to six times with rising temperature before force-accepting, so the filter improves prose without ever starving the story of events. Event and character generation use llama.cpp’s grammar-constrained decoding via the Halfax API, so the JSON envelope is structurally guaranteed — every retry is now a productive prose-quality retry, not a wasted call on malformed output.

Why it's different: Most AI story generators are single-shot — prompt in, text out. This is a persistent, distributed world that evolves autonomously across multiple machines with canonical state, continuity enforcement, semantic memory, health-gated tolerance, and a measurable prose-quality feedback loop. The architecture is closer to an MMO backend than a chatbot.

Halfax AI Stack model serving + ops

Halfax AI is a multi-model, GPU-accelerated intelligence engine built on llama.cpp with Vulkan (Mesa RADV) on AMD gfx1151 (Strix Halo). It runs three LLMs in parallel — Qwen3-Coder (coding), Dark Champion (narrative/reasoning), and Mistral (utility) — each managed by a watchdog that auto-restarts crashed processes. The REST API on port 5000 supports per-request model targeting, automatic failover to available models, and two knowledge layers: a RAG knowledge store (97k+ chunks from PDFs, ZIMs, and text files) for factual context, and MemPalace (ChromaDB semantic memory) for narrative history. Clients can opt into or out of either layer per request. The same API also exposes OpenAI-compatible endpoints (/v1/chat/completions, /v1/completions, /v1/models) with SSE streaming and FIM (fill-in-the-middle) autocomplete, so any tool built for OpenAI works against the local stack unchanged. MemPalace is shared with the Story Universe — the same ChromaDB collection that the Narrative Engine writes to is searchable through the API, giving any connected system access to the full story memory.

Grammar-constrained structured output. The API forwards json_schema and grammar fields through to llama.cpp, which compiles the schema to GBNF and masks illegal tokens at sampling time. The model physically cannot emit output that fails to parse or violates the schema — structured-output reliability becomes a function of vocabulary masking, not prompt discipline. In the Story Universe narrative engine, wiring this into event and character generation dropped the parse-failure retry rate from ~51% of LLM calls to 0%, roughly doubling effective throughput since every parse-retry was a full second-scale generation.

Why it's different: This isn't a hosted API or a wrapper around OpenAI. Three LLMs run simultaneously on local hardware with automatic failover, a built-in watchdog, two independent knowledge layers (RAG + MemPalace), and grammar-constrained JSON decoding for reliable structured output. Everything stays on-prem — no cloud dependency, no token billing, no data leaving the network.

Homelab MCP Server infrastructure monitoring — Python + Paramiko

I built an MCP server that gives my AI assistants structured, real-time access to the entire homelab. It monitors 35+ services across 5 machines (Betelgeuse, hera-pi, Guy, Shop, UYScuti) in under 2 seconds. I built it on the FastMCP framework with Paramiko SSH, connection pooling, and parallel execution.

Local tools: Full Betelgeuse dashboard — systemd services, Docker containers, my AI model endpoints (response timing), GPU telemetry (temperature, power, VRAM via rocm-smi), disk/memory/load, BIND9 DNS, Netbird mesh status, k3d Kubernetes cluster health, and Narrative Engine API.

Fleet tools: SSH-based remote monitoring with YAML-driven host/service configuration. I check systemd units, Docker containers, and processes on Linux; PowerShell Get-Service on Windows. Remote log retrieval, disk/memory inspection, and arbitrary-command execution with a destructive-pattern denylist. SFTP upload/download of files between my workstation and any fleet host via pooled SSH. Connection pooling with 30-second keepalive reuses SSH sessions across tool calls. A ThreadPoolExecutor (8 workers) checks all hosts and their services concurrently.

Story Universe workflow: Dedicated tools orchestrate the multi-host narrative stack end-to-end: storyverse_status checks every component across hosts in parallel, storyverse_check parses the engine log from the last restart marker to report ticks, accept/reject counts, top filter patterns, and active arcs in one call, storyverse_sync_engine rsyncs the running engine to the canonical mirror, and storyverse_new_story archives the current story (HTML + JSON + DB), purges MemPalace narrative memory, resets the world, and restarts services — a full universe reset in a single command.

Site deploy: I manage local mirrors of web properties (like this site). I edit files locally, then the server uploads via SFTP as root and automatically fixes ownership (chown apache:apache) and permissions (chmod 644). Pull, deploy, and status-compare tools keep local and remote in sync.

Safety model: Single-operator trust model — arbitrary commands are allowed on the fleet, blocked only by a tight destructive-pattern denylist (filesystem wipes, disk formats, reboots, fork bombs). Service restarts are gated behind an environment variable. Fleet config hot-reloads on file change — no server restart needed to add hosts or services.

Why it's a good project: MCP is the emerging standard for connecting AI systems to external tools. I turn natural language (“check if hera-pi is healthy”) into structured infrastructure queries across a heterogeneous fleet — Linux and Windows, local and remote, containers and bare metal — with real security controls, not just a shell wrapper. The site deploy workflow means this page was itself edited locally and pushed live through the MCP server.

Halfax System Reporter kernel driver + hardware telemetry

A hardware monitoring platform with a custom Windows kernel driver (WDM, Ring 0) that exposes privileged hardware primitives — MSR read/write, PCI config space, SMBus/I2C — via IOCTL interface with admin-only security descriptors. Not a wrapper around existing tools; the driver (halfax_telemetry_driver.c) loads into the Windows kernel directly.

Three-layer architecture: The kernel driver provides raw hardware access. A C++ user-mode broker (halfax_kernel_broker.cpp) wraps IOCTLs into structured JSON output. Native C helper executables handle specialized hardware reads: cpuid_helper (CPUID intrinsics, P/E core topology, APIC IDs, tile/die/module mapping), spd_helper (RAM SPD EEPROM via I2C — DDR4/DDR5 timings, CAS latency, rank/bank config), nvme_helper (NVMe SMART via kernel IOCTLs — temperature, wear, power-on hours), edid_helper (display EDID parsing via SetupAPI).

CPU telemetry from MSRs: Per-core temperatures with thermal margins, RAPL energy counters for real-time power, turbo ratio analysis, C-state residency tracking, IPC efficiency metrics, and microcode version detection. Multi-method fallback chains on every subsystem (e.g., memory: SPD helper → WMI → dmidecode → kernel).

5,500-line Tkinter GUI with tabbed display across CPU, memory, storage, network, GPU, battery, and system. Cross-platform: Windows (kernel driver + WMI), Linux (sysfs + dmidecode), Raspberry Pi (device tree). Closer to HWiNFO than to a typical Python system info script.

Why it's different: Most system monitors use WMI or /proc and call it done. This one has a custom Windows kernel driver reading MSR registers and PCI config space directly — the same approach commercial tools like HWiNFO use. Writing a WDM driver that loads into Ring 0 is a fundamentally different level of work than calling an API.

Systems & Security

HalfaxOS bare-metal x86_64 OS — from scratch

A 64-bit capability-based operating system written entirely from scratch in C and x86_64 Assembly. No Linux, no BSD, no borrowed kernel code — every line is original. ~413k of hand-written source. Boots via GRUB2 Multiboot2 on both VMware Workstation and physical hardware.

Capability security model: Replaces UNIX file descriptors with typed, permission-checked handles. 512 global kernel objects with refcounting. 128 handles per process with 12-bit permission bitmasks. cap_dup() can only attenuate (reduce) permissions — never escalate. This is the foundational design decision.

Kernel internals: 38 system calls (vs Linux’s 450+). SMP-aware preemptive scheduler with per-process CR3 switching. 4-level paging VMM, bitmap PMM, kernel heap. Message-passing IPC with named ports and structured messages. Ring 3 userspace with ELF64 loader and 5 user programs. ACPI/APIC multi-core CPU detection and IOAPIC routing.

Drivers & networking: Intel E1000 NIC driver, full TCP/IP stack (ARP, IPv4, UDP, TCP, ICMP, DNS, HTTP, DHCP). PS/2 keyboard and mouse. PCI enumeration. PIT timer.

GUI & filesystem: Framebuffer window manager with free-form drag/resize, desktop, taskbar, and multi-window terminal with scrollback. VFS layer with RAM filesystem, device filesystem, and exFAT driver.

Why it's different: This isn't a bootloader someone called an OS. It has a real security thesis — capability-based handles that can only attenuate, never escalate. That's the same direction as Google's Fuchsia and Arm's CHERI. Combined with a TCP/IP stack, a window manager, and Ring 3 userspace, this is a working operating system built from nothing.

Halfax KeySecrets multi-user secrets vault — HTTPS-only

A self-hosted, end-to-end encrypted secrets vault for me, my family, and a couple of trusted friends. Everyone has their own account, their own master password, and their own keypair. The server only ever sees encrypted blobs — even with full database access, an admin can’t read anyone’s passwords.

Sharing is the part most password managers get wrong. KeySecrets does it cryptographically: every secret has its own data key, and that key is sealed individually to each recipient’s public key (X25519 + libsodium SealedBox). Revoking access is just deleting one wrapped key — no re-encryption, no key churn, no leakage. There’s also a hybrid post-quantum mode (X25519 + ML-KEM-768) ready for when classical curves stop being safe.

The crypto stack is conservative and modern: Argon2id for password hashing (memory-hard, the current OWASP pick), ChaCha20-Poly1305 for authenticated encryption everywhere else. Master passwords are never stored; they only ever exist as the input that derives a key, in memory, for the duration of a session.

On the server side it’s a Python/Flask app fronted by cheroot (a production WSGI server with native TLS). HTTPS only, no plaintext port. It runs as a locked-down systemd service with the database credentials kept in a root-owned env file — never in the unit, never in ps. MongoDB sits behind it, holding only ciphertext.

Login is master password plus optional TOTP two-factor from any standard authenticator app. The 2FA secret itself is encrypted with a key derived from the user’s identity key, so even a stolen database doesn’t leak working codes. Failed logins are rate-limited, and every register / login / 2FA / share event lands in an audit log.

The browser side is hardened the way you’d expect a real service to be: HSTS, a strict Content-Security-Policy, clickjacking protection, and Secure/HttpOnly/SameSite cookies. There’s a clean Bootstrap web UI for day-to-day use, a Click-based CLI for scripts, and a documented Bearer-token REST API for everything else. Seven secret types — logins, API keys, SSH keys, notes, certificates, cards, and a free-form custom type — each with its own encrypted fields.

Why it’s a good project: the design started from a threat model, not from “let’s encrypt some stuff.” Right primitives, real cryptographic sharing, post-quantum on-ramp, and the boring-but-essential deployment hygiene most homelab projects skip — production WSGI, TLS-only, 2FA, rate limiting, audit logs, and zero credentials in the unit file.

Halcity city builder — Python + Pygame

A full-featured city builder with a 150×100 procedural terrain world (grass, forest, water). 16 building types, each with subtypes: 5 power plants (Coal, Gas, Nuclear, Solar, Wind), 3 residential (House, Apartment, Villa), 3 commercial (Shop, Office, Mall), 3 industrial (Factory, Warehouse, Tech Lab), and 3 farm variants (Crop, Orchard, Ranch). Buildings must connect to roads to function — roads auto-tile with smart joins (straight, corner, T-junction, crossroad).

The underground layer (Tab toggle) lets you lay water pipes and sewer pipes with a 4-tile Manhattan coverage radius. Water pumps near water tiles produce +15 supply; sewage plants process waste. Both systems affect happiness and pollution.

Turn-based economy simulates population, jobs, food, energy, money, pollution, happiness, water, and sewage every End Turn. Threshold events fire automatically (smog alerts, trade booms, festivals). A prestige system lets you spend points on city decrees (Golden Harvest, Civic Vision, Clean Future). 48×48 pixel-art sprites for every building variant. Cursor-anchored zoom, right-click pan, hover tooltips, and full save/load.

Evolved from a 45,000-line Tkinter prototype into a clean 6-module Pygame architecture: game.py (main loop + world gen), renderer.py (map + UI), game_logic.py (economy + events), sprites.py (pixel art), constants.py (data), ui.py (widgets).

Why it's a good project: City builders look simple but the economy simulation underneath is a real systems problem — interconnected resources with feedback loops, threshold events, and cascading failures. This one models population, jobs, food, energy, money, pollution, happiness, water, and sewage as a coupled system, not independent counters.

newmybad is the current version. It adds a magic system, expanded combat (13k fight.py), a resource loader with JSON data files for weapons, armor, potions, scrolls, wands, jewelry, and monsters, and a full autonomous AI agent:

The Borg AI (borglib.py 61k + borg_policy.py 80k) plays the game autonomously using a goal-stack architecture (LIFO priorities + FIFO deferred goals), BFS pathfinding, stuck/oscillation detection and recovery, and priority-weighted targeting (monsters 40, stairs 30, healing 25, items 20, equip 15, explore 5). Every step is recorded by borg_instrument.py as JSONL telemetry for post-mortem analysis. A partial Godot 4 port exists in godot_version/.

Why it's different: Four iterations of the same game is the interesting part — each one rebuilt to fix what the last got wrong. The final version has a fully autonomous AI player (Borg) with goal-stack planning, oscillation detection, and JSONL telemetry for post-mortem analysis. That's not gameplay modding; it's building an AI agent from scratch.

Skyhaven RPG browser RPG + Godot 4 port

A Skyrim-inspired browser RPG built in pure HTML, CSS, and JavaScript — no frameworks, no build tools. Full character creation with 10 playable races (Nord, Imperial, Dark Elf, High Elf, Wood Elf, Khajiit, Argonian, Orc, Breton, Redguard) and 5 classes (Warrior, Mage, Thief, Ranger, Paladin), each with unique stat bonuses and starting gear.

Turn-based combat (attack, magic, defend, potion, flee), 12 skills across combat/magic/stealth trees, quest log with multi-stage quests, equipment slots, HP/MP/SP resource bars, level-up with attribute point allocation, NPC dialogue trees, world map navigation, and a full save system.

A parallel Godot 4 port is in progress with GDScript reimplementations of the game data, state management, and core scenes (main menu, character creation, game world).

Why it's a good project: Building an RPG with 10 races, 5 classes, and interlocking systems (combat, skills, quests, dialogue, inventory, progression) in vanilla HTML/CSS/JS — no React, no engine — forces you to manage all the state and rendering yourself. The Godot port proves the design transfers to a real game engine.
