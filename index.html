Virtualization & Orchestration Stack

This environment uses a mixed platform strategy so each workload runs on the right abstraction level: containers for portability, orchestration for multi-service systems, and VMs for full OS isolation.

Docker container runtime

  • Supports fast deployment of web apps, APIs, tools, and utility services.
  • How: Images package dependencies once, then run consistently across hosts.
  • Why: Speeds iteration, simplifies updates, and reduces environment drift.
  • Best fit: Stateless apps, service wrappers, scheduled workers, and edge utilities.

Kubernetes (k3d) orchestration layer

  • Supports multi-service systems with scaling, restart logic, and service routing.
  • How: Declarative manifests define desired state; controller loops keep workloads healthy.
  • Why: Better reliability and lifecycle control for complex project stacks.
  • Best fit: Story systems, API groups, and services needing rolling updates and ingress.

Hyper-V windows virtualization

  • Supports full guest operating systems on the Windows workstation.
  • How: Native hypervisor integration provides virtual switching, isolation, and snapshots/checkpoints.
  • Why: Safe testing for OS-level changes without risking the primary host setup.
  • Best fit: Windows-native lab scenarios, network simulation, and system behavior testing.

VMware Workstation cross-os VM lab

  • Supports parallel Linux VM environments for toolchains and integration tests.
  • How: Snapshot-driven workflows enable quick rollback and repeatable test states.
  • Why: Great for controlled experiments, compatibility validation, and sandboxing.
  • Best fit: Multi-node simulations, distro comparisons, and pre-deployment verification.

AI & Story

Story Universe Ecosystem distributed narrative system

A distributed, AI-driven narrative world that runs continuously across three hosts. The Chronicle Keeper (hera-pi, Raspberry Pi 5) holds canonical world state — characters, factions, locations, events — in SQLite, and broadcasts a world clock via ZeroMQ pub/sub. The Narrative Engine (Betelgeuse) subscribes to those ticks and generates arcs and events through the Halfax AI API, targeting Dark Champion. The World Browser (Guy VPS) presents the live chronicle as a public dashboard reading from both the Chronicle Keeper REST API and the arcs API.

Connecting them is MemPalace — a ChromaDB-backed semantic memory framework co-created by actress Milla Jovovich and engineer Ben Sigman, designed to give AI models long-term memory that mimics human spatial recall (organized into wings and rooms). Every accepted story event and arc update is written to MemPalace in real time. Before each generation call, the engine searches MemPalace for relevant past events and injects them as narrative context, so the LLM builds on what happened before rather than generating in isolation. When a story is archived, MemPalace is purged so the next story starts with a clean slate.

Prose-quality pipeline. Every generated event passes through a post-generation regex filter that rejects atmospheric-formula openings (“Dawn sunlight filters through the windows…”), tension-family clichés, and time-of-day contradictions. Rejected attempts feed back into the next retry as real-time negative examples, letting the LLM escape its trained reflexes. Up to six retries with rising temperature before force-accept. JSON envelopes are guaranteed-valid via grammar-constrained decoding at the API boundary — every retry is now a productive prose-quality retry, not a wasted call on malformed output (parse failures dropped from ~51% to 0%).

Health-gated tolerance — the world pauses, it never lies. All services auto-start under systemd with infinite retry. A HealthMonitor probes the Chronicle Keeper and LLM endpoints every tick — if either is unhealthy, the engine pauses instead of fabricating events, and resumes silently when dependencies recover. There is no template fallback: when the LLM is down, the universe simply waits.

Why it’s different: most AI story generators are single-shot — prompt in, text out. This is a persistent, distributed world that evolves autonomously across three machines with canonical state, ZeroMQ-synchronized continuity, semantic memory the LLM actually consults, health-gated tolerance with no fabrication path, and a measurable prose-quality feedback loop. The architecture is closer to an MMO backend than a chatbot.

Halfax AI Stack multi-model serving + ops

A multi-model GPU-accelerated inference server built on llama.cpp with Vulkan (Mesa RADV) on AMD gfx1151 (Strix Halo), 96 GB unified VRAM. Three LLMs serve concurrently — Qwen3-Coder (code), Dark Champion (narrative + reasoning), Mistral (utility) — loaded VRAM-largest-first to minimize fragmentation, each under a Python supervisor that auto-restarts on crash. The API exposes OpenAI-compatible endpoints (/v1/chat/completions, /v1/completions with fill-in-the-middle, /v1/models) plus per-request model targeting and automatic failover, so any Copilot/Cursor/Continue-class client plugs in unchanged.

Three independent memory layers, opt-in per request. A 99,000-chunk RAG knowledge store over my PDFs, offline encyclopedia archives, and notes — searched via an hnswlib approximate-nearest-neighbor index for ~4 ms median latency (down from ~50 ms linear scan), with embeddings cached per chunk by SHA-256 of chunk text rather than file mtime — so adding or removing one document only re-embeds that document, never the whole library. MemPalace, a ChromaDB-backed long-term memory store organized into wings and rooms, shared with the Story Universe so any connected system can search the full narrative timeline. And a two-tier personal memory: a 60-bullet always-loaded CORE file for rules, identity, preferences, and active context, plus an unbounded archive auto-retrieved per turn by cosine similarity above a configurable threshold.

Grammar-constrained structured output. The API forwards json_schema and grammar fields through to llama.cpp, which compiles them to GBNF and masks illegal tokens at sampling time — the model is physically blocked, token by token, from emitting output that would fail to parse or violate the schema. In the Story Universe narrative engine, wiring this into event and character generation dropped the parse-failure retry rate from ~51% of LLM calls to 0%, roughly doubling effective throughput.

Vulkan-accelerated embeddings via dedicated supervised process. A second llama-server on port 5001 runs all-MiniLM-L6-v2 (converted to GGUF, F16, mean-pooled) on the same Mesa RADV backend — necessary because Python sentence-transformers hangs indefinitely on HIP device init on gfx1151. Same watchdog and auto-restart pipeline as the chat models. Routing embeddings through llama.cpp’s Vulkan path bypasses the broken ROCm path entirely.

Why it’s different: Not a wrapper. Three concurrent LLMs under one supervisor with VRAM-ordered loading and automatic failover, three independent memory layers clients can opt into per request, grammar-constrained decoding for guaranteed-valid structured output, HNSW-indexed RAG with content-keyed caching, and the embedding path engineered around a real driver bug. Engineered end-to-end — the locality is incidental; the architecture is the point.

Halfax AI VSCode Extension native IDE client — TypeScript

A native VSCode extension for AI-assisted coding — chat, autonomous agent, fill-in-the-middle autocomplete, one-click apply on suggested edits, Cmd+K inline rewrites — running end-to-end against my own AI server. Not a Continue.dev fork or wrapper around someone else’s protocol: written from scratch in TypeScript with custom React UI, Zustand state, an in-process MCP stdio client (@modelcontextprotocol/sdk), and direct OpenAI-compatible streaming.

Agent loop runs in-extension as a six-state finite state machine (pending → in_progress → completed | awaiting_user | error | cancelled) driving multi-step work via a strict JSON tool-call protocol. The extractor tolerates common model formatting mistakes (stray trailing braces, fence variations, missing args), the validator normalizes no-arg tool calls before rejecting, and consecutive-error thresholds pause cleanly into awaiting_user instead of spinning. Mid-turn checkpointing: every successful turn flushes the agent’s history to disk before the next, so quit-mid-task or crash-mid-task is recoverable — reopening VSCode auto-resumes the agent from where it stopped.

Single-slot priority request queue across the entire extension. The local llama.cpp backend has one GPU inference slot at a time; the queue prioritizes FIM=0 < chat=1 < agent=2, so a long-running agent task never starves typing-time autocomplete and a chat reply doesn’t wait behind a background completion. Apply on suggested edits routes through vscode.diff for preview and writes via the MCP file_write tool with expected_mtime conflict detection (in seconds, not milliseconds — FileStat.mtime/1000); falls back to native:write if the MCP path is unavailable. The write fails if the file changed on disk between read and save.

Persistent memory + skills + hooks — all file-resident. /remember writes to a CORE file always loaded into chat plus an embedding-searched archive auto-injected per turn. Skills are markdown files in ~/.halfax/skills/ with a tiny frontmatter (name / description / mode) parsed in-process; they appear instantly as slash commands with a popover palette in the composer. Lifecycle hooks (on-session-start, on-tool-call, on-stop) run shell commands of my choice with structured event variables (HALFAX_EVENT, HALFAX_TOOL, HALFAX_REASON, etc.). Self-update pulls a new VSIX from my homelab, streams it to disk, and installs through workbench.extensions.installExtension.

How the agent differs from Claude Code, Windsurf Cascade, and GitHub Copilot. Those three send every keystroke and chat to a corporate cloud — account-required, telemetry-by-default, per-token or per-seat billing, hard rate and context limits, dead without internet. Mine: every inference on my own GPU, every chat saved as a plain JSON file under ~/.halfax-sessions/, every memory bullet a line in a CORE.md I can edit. The agent FSM is visible in the UI and pauseable mid-loop; every destructive tool call hits a per-call permission prompt by default (vs Copilot’s autonomous-by-default agent). Mid-turn checkpointing for crash recovery is something none of the three commercial agents offer. Skills, hooks, memory, and the update channel are all configured by editing files in ~/.halfax/, not by clicking through a vendor settings UI.

Why it’s a good project: the full IDE assistant surface — chat, autonomous agent, autocomplete, inline edits, sessions, skills, hooks, persistent memory, self-update — built end-to-end in TypeScript with a real state machine, real conflict-aware writes, real crash recovery, and real priority scheduling. Not a thin client over someone else’s API.

Halfax System Reporter kernel driver + hardware telemetry

A hardware monitoring platform with a custom Windows kernel driver (WDM, Ring 0) that exposes privileged hardware primitives — MSR read/write, PCI config space, SMBus/I2C — via IOCTL interface with admin-only security descriptors. Not a wrapper around existing tools; the driver (halfax_telemetry_driver.c) loads into the Windows kernel directly. Same access level commercial tools like HWiNFO use, written from scratch.

Three-layer architecture. The kernel driver provides raw hardware access. A C++ user-mode broker (halfax_kernel_broker.cpp) wraps IOCTLs into structured JSON output. A set of native C helper executables handle specialized hardware reads: cpuid_helper (CPUID intrinsics, P/E core topology, APIC IDs, tile/die/module mapping), spd_helper (RAM SPD EEPROM via I2C — DDR4/DDR5 timings, CAS latency, rank/bank config), nvme_helper (NVMe SMART via kernel IOCTLs — temperature, wear, power-on hours), edid_helper (display EDID parsing via SetupAPI).

What it pulls from MSRs: per-core temperatures with thermal margins, RAPL energy counters for real-time power, turbo ratio analysis, C-state residency tracking, IPC efficiency metrics, microcode version detection. Multi-method fallback chains on every subsystem (e.g., memory: SPD helper → WMI → dmidecode → kernel) — if the deepest method fails, the app tries each fallback in turn before giving up, so even on locked-down systems most readings are still available.

5,500-line Tkinter GUI with tabbed display across CPU, memory, storage, network, GPU, battery, and system. Cross-platform with full feature parity: Windows (kernel driver + WMI), Linux (sysfs + dmidecode), Raspberry Pi (device tree). Closer to HWiNFO than to a typical Python sysinfo script.

Why it’s different: most system monitors use WMI or /proc and call it done. This one has a custom WDM driver reading MSR registers and PCI config space directly — the same approach commercial tools use, but written from scratch. Writing a kernel driver that loads into Ring 0 is a fundamentally different level of work than calling an API.

Systems & Security

HalfaxOS bare-metal x86_64 OS — from scratch

A 64-bit capability-based operating system written entirely from scratch in C and x86_64 Assembly. No Linux, no BSD, no borrowed kernel code — every line is original. About 413k lines of hand-written source. Boots via GRUB2 Multiboot2 on both VMware Workstation and physical hardware.

Capability security model. Replaces UNIX file descriptors with typed, permission- checked handles. 512 global kernel objects with refcounting; 128 handles per process with 12-bit permission bitmasks. cap_dup() can only attenuate (reduce) permissions — never escalate. This is the foundational design decision and makes whole classes of security bugs structurally impossible. Same direction as Google Fuchsia and ARM CHERI.

Kernel internals. 38 system calls (vs Linux’s 450+). SMP-aware preemptive scheduler with per-process CR3 switching. 4-level paging VMM, bitmap PMM, kernel heap. Message-passing IPC with named ports and structured messages. Ring 3 userspace with ELF64 loader and 5 user programs. ACPI/APIC multi-core CPU detection and IOAPIC routing.

Drivers and networking. Intel E1000 NIC driver. Full from-scratch TCP/IP stack: ARP, IPv4, UDP, TCP, ICMP, DNS, HTTP, DHCP. PS/2 keyboard and mouse. PCI enumeration. PIT timer.

GUI and filesystem. Framebuffer window manager with free-form drag/resize, desktop, taskbar, multi-window terminal with scrollback. VFS layer with RAM filesystem, device filesystem, and exFAT driver.

Why it’s different: not a bootloader someone called an OS. A real security thesis — capability handles that can only attenuate — in the same direction as Fuchsia and CHERI. Combined with a working TCP/IP stack, a window manager, ELF64 user programs in Ring 3 isolation, and IOAPIC-routed multicore. A working operating system built from nothing.

Halfax KeySecrets multi-user secrets vault — HTTPS-only

A self-hosted, end-to-end encrypted secrets vault for me, my family, and a couple of trusted friends. Everyone has their own account, their own master password, and their own keypair. The server only ever sees ciphertext — even with full database access, an admin cannot read anyone’s passwords.

Per-recipient cryptographic sharing. Sharing is the part most password managers get wrong. KeySecrets does it cryptographically: every secret has its own data key, and that key is sealed individually to each recipient’s public key (X25519 + libsodium SealedBox). Revoking access is just deleting one wrapped key — no re-encryption, no key churn, no leakage. There’s also a hybrid post-quantum mode (X25519 + ML-KEM-768) ready for when classical elliptic-curve crypto stops being safe.

Conservative modern crypto stack. Argon2id for password hashing (memory-hard, the current OWASP pick — GPU-resistant). ChaCha20-Poly1305 for authenticated encryption everywhere else. Master passwords are never stored; they only ever exist as the input that derives a session key, in memory, for the duration of a session.

Login + 2FA. Master password plus optional TOTP two-factor from any standard authenticator app. The 2FA secret itself is encrypted with a key derived from the user’s identity key, so even a stolen database doesn’t leak working codes. Failed logins are rate-limited; every register / login / 2FA / share event lands in an audit log.

Production hygiene most homelab projects skip. Python/Flask app fronted by cheroot (production WSGI server with native TLS). HTTPS only — no plaintext port. Locked-down systemd service with database credentials in a root-owned env file (never in the unit, never in ps). MongoDB sits behind it, holding only ciphertext. Browser side: HSTS, strict Content-Security-Policy, clickjacking protection, Secure/HttpOnly/SameSite cookies. Three interfaces — web UI, Click-based CLI, documented Bearer-token REST API. Seven secret types (logins, API keys, SSH keys, notes, certificates, cards, free-form), each with its own encrypted fields.

Why it’s a good project: the design started from a threat model, not from “let’s encrypt some stuff.” Right primitives, real cryptographic sharing, post-quantum on-ramp, and the boring-but-essential deployment hygiene — production WSGI, TLS-only, 2FA, rate limiting, audit logs, and zero credentials in the unit file.

Halcity city builder — Python + Pygame

A full-featured city builder with a 150×100 procedural terrain world (grass, forest, water). 16 building types, each with subtypes: 5 power plants (Coal, Gas, Nuclear, Solar, Wind), 3 residential (House, Apartment, Villa), 3 commercial (Shop, Office, Mall), 3 industrial (Factory, Warehouse, Tech Lab), and 3 farm variants (Crop, Orchard, Ranch). Buildings must connect to roads to function — roads auto-tile with smart joins (straight, corner, T-junction, crossroad).

The underground layer (Tab toggle) lets you lay water pipes and sewer pipes with a 4-tile Manhattan coverage radius. Water pumps near water tiles produce +15 supply; sewage plants process waste. Both systems affect happiness and pollution.

Turn-based economy simulates population, jobs, food, energy, money, pollution, happiness, water, and sewage every End Turn. Threshold events fire automatically (smog alerts, trade booms, festivals). A prestige system lets you spend points on city decrees (Golden Harvest, Civic Vision, Clean Future). 48×48 pixel-art sprites for every building variant. Cursor-anchored zoom, right-click pan, hover tooltips, and full save/load.

Evolved from a 45,000-line Tkinter prototype into a clean 6-module Pygame architecture: game.py (main loop + world gen), renderer.py (map + UI), game_logic.py (economy + events), sprites.py (pixel art), constants.py (data), ui.py (widgets).

Why it's a good project: City builders look simple but the economy simulation underneath is a real systems problem — interconnected resources with feedback loops, threshold events, and cascading failures. This one models population, jobs, food, energy, money, pollution, happiness, water, and sewage as a coupled system, not independent counters.

Roguelike Dungeon Crawlers 4 iterations — mybad → newmybad

A roguelike dungeon crawler that evolved through four major iterations, each building on the last:

newmybad is the current version. It adds a magic system, expanded combat (13k fight.py), a resource loader with JSON data files for weapons, armor, potions, scrolls, wands, jewelry, and monsters, and a full autonomous AI agent:

The Borg AI (borglib.py 61k + borg_policy.py 80k) plays the game autonomously using a goal-stack architecture (LIFO priorities + FIFO deferred goals), BFS pathfinding, stuck/oscillation detection and recovery, and priority-weighted targeting (monsters 40, stairs 30, healing 25, items 20, equip 15, explore 5). Skyhaven RPG browser RPG + Godot 4 port

A Skyrim-inspired browser RPG built in pure HTML, CSS, and JavaScript — no frameworks, no build tools. Full character creation with 10 playable races (Nord, Imperial, Dark Elf, High Elf, Wood Elf, Khajiit, Argonian, Orc, Breton, Redguard) and 5 classes (Warrior, Mage, Thief, Ranger, Paladin), each with unique stat bonuses and starting gear.

Turn-based combat (attack, magic, defend, potion, flee), 12 skills across combat/magic/stealth trees, quest log with multi-stage quests, equipment slots, HP/MP/SP resource bars, level-up with attribute point allocation, NPC dialogue trees, world map navigation, and a full save system.

A parallel Godot 4 port is in progress with GDScript reimplementations of the game data, state management, and core scenes (main menu, character creation, game world).

Why it's a good project: Building an RPG with 10 races, 5 classes, and interlocking systems (combat, skills, quests, dialogue, inventory, progression) in vanilla HTML/CSS/JS — no React, no engine — forces you to manage all the state and rendering yourself. The Godot port proves the design transfers to a real game engine.
