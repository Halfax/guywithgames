Virtualization & Orchestration Stack

This environment uses a mixed platform strategy so each workload runs on the right abstraction level: containers for portability, orchestration for multi-service systems, and VMs for full OS isolation.

Docker container runtime

  • Supports fast deployment of web apps, APIs, tools, and utility services.
  • How: Images package dependencies once, then run consistently across hosts.
  • Why: Speeds iteration, simplifies updates, and reduces environment drift.
  • Best fit: Stateless apps, service wrappers, scheduled workers, and edge utilities.

Kubernetes (k3d) orchestration layer

  • Supports multi-service systems with scaling, restart logic, and service routing.
  • How: Declarative manifests define desired state; controller loops keep workloads healthy.
  • Why: Better reliability and lifecycle control for complex project stacks.
  • Best fit: Story systems, API groups, and services needing rolling updates and ingress.

Hyper-V windows virtualization

  • Supports full guest operating systems on the Windows workstation.
  • How: Native hypervisor integration provides virtual switching, isolation, and snapshots/checkpoints.
  • Why: Safe testing for OS-level changes without risking the primary host setup.
  • Best fit: Windows-native lab scenarios, network simulation, and system behavior testing.

VMware Workstation cross-os VM lab

  • Supports parallel Linux VM environments for toolchains and integration tests.
  • How: Snapshot-driven workflows enable quick rollback and repeatable test states.
  • Why: Great for controlled experiments, compatibility validation, and sandboxing.
  • Best fit: Multi-node simulations, distro comparisons, and pre-deployment verification.

Network Stack

The network layer is built around private service discovery, encrypted cross-host transport, and clear role boundaries between local hardware and cloud nodes.

BIND9 Implementation private DNS authority

  • BIND9 serves as the authoritative resolver for my private lab zone.
  • How: Internal records map service names to private endpoints for predictable routing.
  • Why: Stable hostnames let projects move between nodes without rewriting app configs.
  • Result: Cleaner operations, easier service migrations, and less hardcoded addressing.

NetBird VPN Usage wireguard mesh overlay

  • NetBird provides encrypted peer-to-peer connectivity between home lab nodes and VPS hosts.
  • How: A mesh overlay makes each machine reachable as if on one secure private fabric.
  • Why: Services can communicate directly without exposing internal APIs to the public internet.
  • Result: Safe cross-site traffic for orchestration, data sync, and service-to-service requests.

Hardware Interaction Model right workload, right node

  • Betelgeuse handles heavy compute, model inference, and orchestration.
  • UYScuti focuses on development, game builds, and workstation-class experiments.
  • hera-pi runs lightweight utility services and always-on support tasks.
  • Cloud hosts provide public entry points while private internals stay on the mesh.

  • Named DNS services + mesh routing make multi-node projects composable and maintainable.
  • Container and VM platforms can consume the same internal network conventions.
  • Public and private planes stay separated: internet-facing UX, private backend control paths.
  • This architecture supports AI apps, story systems, monitoring tools, and game services together.

AI & Story

Story Universe Ecosystem a fictional world that writes itself

The Story Universe is a fictional world that runs by itself, around the clock, generating its own stories — and it’s built across three different computers in my homelab, each doing one job. The Chronicle Keeper (running on a small Raspberry Pi) is the world’s record-keeper — it holds the master list of every character, faction, location, and past event in a database, and broadcasts a steady “tick” like a clock so every other machine stays in sync. The Narrative Engine (running on my main server, Betelgeuse) listens for those ticks and uses the Halfax AI server to generate the next story event or arc each time. The World Browser (running on my cloud-hosted server) is a public web page that shows the live chronicle as it’s being written — anyone can watch.

What ties it all together is MemPalace, a long-term memory store organized like rooms in a building (it was co-designed by actress Milla Jovovich and engineer Ben Sigman). Every story event is written into MemPalace as soon as it’s accepted; before the AI writes the next event, the engine searches MemPalace for related past events and feeds them in as background — so the AI actually builds on what happened before, instead of forgetting and contradicting itself. When I archive a finished story, MemPalace is wiped so the next story starts with a clean slate.

If something breaks, the world pauses — it never lies. A health monitor checks the Chronicle Keeper and the AI server on every tick. If either is unhealthy, the engine stops generating events and waits silently for the dependency to recover. There is no fake fallback — if the AI is down, the universe simply pauses, then picks up where it left off when service returns.

It writes better when it gets feedback. Every generated paragraph runs through a quality filter that rejects clichéd openings (“Dawn sunlight filters through the windows…”), overused tension phrases, and time-of-day contradictions. The reasons it was rejected get fed back into the next attempt as real-time examples of what not to do. The engine tries up to six times with rising creativity before giving up, so quality goes up without ever starving the story of new events. Combined with the AI server’s “model can’t produce broken JSON” mode, this dropped wasted retries from 51% of all calls down to zero — every retry now goes toward better writing, not toward fixing the format.

Why it’s different: Most AI story generators are one-shot — you give a prompt, you get text, and that’s the end. This is a persistent, evolving world spread across multiple machines, with a single source of truth for what’s happened, long-term memory the AI actually uses, self-pausing when dependencies fail, and a feedback loop that demonstrably improves prose quality. The architecture is closer to an online game’s backend than to a chatbot.

Halfax AI Stack my own AI server, running at home

Halfax AI is my own AI “brain” that runs on my own computer instead of on someone else’s cloud. It serves three different AI models at once — one tuned for writing code (Qwen3-Coder), one for story-writing and reasoning (Dark Champion), and one general-purpose model (Mistral) — all sharing the same GPU. A small “watchdog” program keeps an eye on each model and instantly restarts any that crash, so the service stays up around the clock.

Apps connect to it through a normal web address (port 5000) and pick which model they want for each request. If their first choice is busy or unavailable, it automatically hands the request to a working model so nothing fails silently. Crucially, the API speaks the same “OpenAI dialect” that most commercial AI tools were built for — meaning any editor, chatbot, or script that was written to talk to ChatGPT can be pointed at my server and it just works, with no code changes. That includes type-ahead autocomplete in code editors, which uses a separate “fill-in-the-middle” mode the server also exposes.

Two kinds of memory, on top of the model. The model itself is fixed once it’s downloaded — it doesn’t learn from chats. So I built two memory layers around it. The first is a knowledge library of about 99,000 chunks pulled from my PDFs, offline encyclopedia archives, and text files; when you ask a question, the server finds the most relevant pages and feeds them to the model as context. The second is MemPalace, a long-term memory store organized like rooms in a building — the Story Universe writes every story event into it, and any connected app can later search those events to keep narratives consistent across days, weeks, or months.

Persistent personal memory (added 2026-05-01). A new layer sits on top of those: a two-tier memory of facts about me. A small “CORE” file is loaded into every conversation — rules I’ve told it (“always use a Python virtual environment”), standing facts (“Holly is my wife”), preferences, and current-work context, capped at 60 short bullets so it stays cheap. Below that, an unlimited “archive” of older notes is searched automatically based on what I’m asking. Identical entries are caught and refused so the same fact can’t be saved twice. The result: the AI actually remembers me across sessions, the way ChatGPT’s memory feature works — except every byte stays on my disk and I can read it in a text editor.

Why the embedding service is its own process. Turning text into the long lists of numbers (“embeddings”) needed for memory search has to be fast. The standard Python library for that kept hanging indefinitely on my GPU because the AMD driver path it used was broken for my chip. So I run a dedicated llama.cpp server just for embeddings — same GPU, different driver path, same watchdog keeping it alive. Search latency dropped from about 50 milliseconds per query to about 4 milliseconds after I added a fast-lookup index, and embeddings are cached so adding or removing one document only re-processes that document’s pages, not the whole library.

The model literally can’t produce broken output. When I need structured data back (like a JSON object with specific fields), the server can hand the model a strict template at generation time. The model is then blocked at the per-letter level from typing anything that would break the format. In the story engine, this dropped JSON parse failures from about 51% of all calls down to zero — effectively doubling throughput, because every previously-wasted retry now produces useful output.

Why it’s different: This isn’t a wrapper around someone else’s cloud service. Three AI models run side-by-side on my own hardware with automatic failover, a watchdog that self-heals on crash, two layers of memory the AI can search, persistent personal memory that survives restarts, and a system that physically prevents the AI from producing broken JSON. Nothing leaves the network. No monthly fee. No tokens billed. No data sent to anyone.

Halfax AI VSCode Extension my own AI assistant inside the editor

I built my own AI coding assistant, the same kind you’d get from GitHub Copilot, Cursor, or Claude Code — except mine runs entirely on my own machine. No cloud round-trip. No login. No per-token bill. No corporate telemetry. It plugs into VSCode like any other extension and gives me a chat sidebar, an autonomous “agent” mode, type-ahead autocomplete, and one-click code edits, all powered by the three local AI models on my own server.

Agent mode — the AI works on its own. When I switch the sidebar to Agent mode and give it a task like “read the README and fix the broken test,” the AI runs by itself in a loop: it thinks about what to do next, calls a tool (read a file, list a directory, run a shell command), looks at the result, and decides the next step — for as many turns as the job takes. Every tool the agent wants to use shows up as a card in the chat with the arguments it intends to use, and I can approve once, approve always, or refuse. If something goes wrong three times in a row, the agent pauses and asks me what to do instead of spinning forever.

One-click apply & Cmd+K inline edits. When the assistant suggests a code change, an Apply button appears next to the code block. Click it and a side-by-side diff opens so I can see exactly what will change before I accept. The write checks the file’s last-modified time first — so if I edited the file by hand in the meantime, it refuses to overwrite my work. Pressing Cmd+K on any selection lets me type a natural-language instruction (“rename this to camelCase,” “add error handling”), and the model rewrites just that selection inside a diff preview.

Type-ahead autocomplete with smart priority. The same coding model powers inline autocomplete suggestions as I type. The AI server has only one “slot” on the GPU at a time, so the extension uses a priority queue: anything I just typed in chat preempts background autocomplete, and an explicit agent task preempts both. That means chat never gets stuck waiting for an autocomplete request to finish first.

Chat sessions auto-save and auto-resume. Two tree views in the sidebar list every chat session and every agent task I’ve ever run. Every reply, tool call, and search is written to a small JSON file on disk as it happens, so closing VSCode doesn’t lose anything — even if the editor crashes mid-task, reopening it restores the conversation and the agent picks up from where it left off. Hit “New Session” to start fresh.

@knowledge: ask my own document library. Type @knowledge how does WireGuard work in the chat box and the extension skips the AI model entirely — it searches my local 99k-chunk knowledge library (PDFs, offline encyclopedias, text files) and shows the most relevant passages directly with scores and sources. A 👍 / 👎 button under each AI reply lets me give feedback that gets logged for future fine-tuning.

Skills and hooks (added 2026-05-01). I can drop a markdown file into ~/.halfax/skills/ with a name and instructions and it instantly becomes a slash command in the chat box — same idea as Claude Code’s skills, except the file lives on my disk and I edit it like any other text file. The extension also runs shell commands of my choice on lifecycle events (session start, tool call, agent stop), letting me wire up logging, backups, or alerts without touching the extension’s source code.

Persistent personal memory (added 2026-05-01). The same two-tier memory the AI server holds — CORE rules and a long-term archive — is wired into the chat sidebar. Type /remember always use venv when running Python and that rule gets saved to disk and loaded into every future conversation, the way Claude Code remembers things across sessions. Identical entries are caught and refused so the same fact can’t pile up. The full memory file is a plain text file I can read with any editor.

Self-update from my homelab (added 2026-05-01). When I ship a new version, “Halfax: Check for Update” in the command palette downloads the new package straight from my server, installs it, and prompts to reload the window — no marketplace, no account, no review queue.

How this is different from Claude Code, Windsurf, and GitHub Copilot. All three of those send every keystroke and every chat to a corporate cloud and bill per token or per seat. They require an account, run telemetry by default, and put hard limits on context size and request rate. Mine: every inference happens on my own GPU, every chat is saved as a plain JSON file in my home directory, every memory is a text bullet on my disk, and the entire thing keeps working with the internet completely unplugged. The agent state machine is more transparent — I can watch it move through its six states (pending → in_progress → completed | awaiting_user | error | cancelled) and pause it at any time. Every destructive tool call (writes, deletes, shell commands) hits a permission prompt by default rather than running automatically. Skills, hooks, and self-update mirror Claude Code’s design but everything is configured by editing files in my own home directory, not by clicking through a vendor’s settings UI. And there’s no marketplace review process — I ship a new version to myself by pushing a file to my homelab.

Why it’s a good project: The full IDE coding-assistant surface — chat, autonomous agent, autocomplete, inline edits, feedback, sessions, custom skills, lifecycle hooks, persistent memory, self-update — without a single byte leaving the box. Most assistants in this space are thin layers over a cloud API; this one is a complete, self-hosted parallel of that whole ecosystem, designed to be readable, repairable, and owned end-to-end.

Homelab MCP Server tells my AI what every machine is doing

I can ask my AI assistant something like “is the Raspberry Pi okay?” or “why is the website slow?” and it actually checks — in real time. This server is the bridge that lets the AI talk to all five computers in my homelab. It uses an open standard called MCP (Model Context Protocol) which is becoming the universal way for AI assistants to plug into outside systems — the same protocol Claude Code uses to access tools. Mine checks 35+ services across all 5 of my machines in under 2 seconds.

What it can see on my main server: all running services, every Docker container, every AI model endpoint (with response times), GPU temperature / power draw / memory usage, disk and memory and CPU load, the home DNS server, the VPN mesh status, the Kubernetes cluster, and the Story Universe engine.

What it can do remotely: The server logs in to the other machines over SSH (cleanly re-using connections so it’s fast). It can list services, check Docker containers, pull recent log files, look at disk and memory, and run arbitrary commands — with a hard-coded blocklist that refuses anything destructive (“wipe the disk,” “reboot,” etc.). It works on Linux and Windows. It can also upload and download files between machines, check security alerts and SMART drive health, and stream the last few hours of any logfile. All in plain English from the chat sidebar.

One-command Story Universe operations: Tools wired specifically for the Story Universe stack. Status checks every component across the three hosts at once. Check reads the engine’s log and reports how many story ticks ran, how many events were accepted or rejected, and which filters fired most. Sync copies the running engine to the canonical mirror. New story archives the current story to HTML and JSON, wipes the long-term memory, resets the world clock, and restarts all services — a complete fresh start in a single command.

Site deploy: I edit my websites locally on my workstation, and the server uploads them to the live web hosts over SSH, automatically fixing file ownership and permissions on the way in. It can also pull files back from the live host if I made a quick fix in the wrong place. This page was itself edited locally and pushed live through these tools.

Safety: Since I’m the only operator, the server is permissive on purpose — but destructive commands (filesystem wipes, disk formats, reboots, fork bombs) are blocked by pattern. Service restarts require an environment flag set on purpose. The fleet config (which machines, which services to check) lives in a YAML file that the server re-reads automatically when it changes — no restart needed to add a new host.

Why it’s a good project: MCP is the new standard for connecting AI assistants to real-world tools, and most examples online are toy demos. This one runs against a real, mixed fleet — Linux and Windows, local and remote, containers and bare metal — with actual security controls instead of just a shell wrapper. Natural-language requests turn into structured queries across the whole infrastructure, and the AI gets answers it can act on.

Halfax System Reporter a deep-dive hardware monitor I built

A tool that tells me everything about a computer’s hardware — per-core CPU temperatures, real-time power draw, exact memory timings, drive wear, GPU details, battery health, display info — all in one window. The trick is that a lot of that information is locked behind privileged operating-system layers most apps can’t touch. So I wrote my own Windows kernel driver — a small piece of code that loads into the deepest, most-protected layer of the operating system, where it’s allowed to read directly from the CPU’s internal sensors and the motherboard’s low-level chips. The user-facing app then talks to my driver to pull readings the same way commercial tools like HWiNFO do.

Three layers stacked together. The kernel driver is the bottom layer that reads the hardware directly. A program above it translates raw readings into clean structured data (JSON). On top, small specialized programs handle individual subsystems: one reads CPU identity and core layout, one reads memory module timing chips, one reads SSD health (temperature, wear, hours powered on), one reads display info (model, native resolution).

What it pulls from CPU registers: per-core temperature with thermal margins, real-time wattage, turbo-boost analysis, how often each core is idle vs busy, microcode version. Each subsystem has multiple fallback paths — if the deep driver method fails, the app tries Windows’ built-in APIs, then a third method, before giving up. So even on locked-down systems, you still see most of the information.

A 5,500-line graphical interface organizes everything into tabs: CPU, memory, storage, network, GPU, battery, system. The same app runs on Windows (with the kernel driver), Linux (using its native system files), and Raspberry Pi (reading the device-tree).

Why it’s different: Most system monitors are wrappers around the operating system’s public information — they show you what Windows is willing to reveal. This one includes a custom kernel driver that reads CPU sensors and motherboard chips directly — the same approach the well-known commercial tools use, but written from scratch. Writing a kernel driver that loads into the most-privileged layer of Windows is a fundamentally different level of work than calling an API.

Systems & Security

HalfaxOS a real operating system, written from nothing

A complete 64-bit operating system written entirely from scratch — no Linux, no BSD, no borrowed code anywhere. About 413,000 lines of original C and Assembly. It boots on real hardware (and inside a virtual machine) using a standard bootloader called GRUB2.

Built around “permissions can only shrink, never grow.” Every operating system has to decide how programs ask for access to files, network, and hardware. Most use the same decades-old design (file descriptors). HalfaxOS uses a newer one called capability-based security: instead of asking the OS “please open this file,” a program holds typed permission tickets it can pass to other programs — but the act of handing a ticket can only reduce what the receiver can do, never give them more than the sender had. This makes entire classes of security bugs structurally impossible. It’s the same direction Google’s Fuchsia OS and the experimental ARM CHERI architecture are heading.

What’s inside: A scheduler that fairly time-shares programs across CPU cores (with proper memory isolation between them). A virtual-memory manager that uses 4 levels of page tables. A messaging system so programs can talk to each other through named “ports.” A user-program loader that runs untrusted code in the lower-privilege layer the CPU exposes. The kernel offers 38 different system services — for comparison, Linux exposes more than 450, so this is small and focused.

Drivers and networking: A driver for Intel network cards, plus a full TCP/IP networking stack so the OS can actually browse the internet (ARP, IPv4, UDP, TCP, ICMP, DNS, HTTP, DHCP — all written from scratch). Keyboard and mouse drivers. PCI device enumeration. A timer.

It also has a desktop: A graphical window manager — you can drag windows around, resize them, use a desktop and a taskbar, and open multiple terminals with scrolling history. There’s a virtual file-system layer that supports a temporary in-RAM filesystem, a special filesystem for devices, and a real-disk format (exFAT).

Why it’s different: This isn’t a basic “hello world” bootloader someone called an OS. It has a real security thesis — permissions that can only shrink — the same direction next-generation systems like Google Fuchsia and ARM CHERI are taking. Combined with a full networking stack, a window manager, and the ability to run user programs in CPU-enforced isolation, this is a working operating system built from nothing.

ComboServer does internet outages hurt video-game sales?

A research-style analytics platform that asks a question nobody has built proper tools for: do internet routing problems actually affect gaming? It watches the “road map” of the internet (the live data feed that shows which networks can reach which) and at the same time watches Steam — the player counts, reviews, and traffic patterns of every game — then looks for real connections between the two. Things like: an internet outage in a country, followed by a player drop on Steam in that region. A network misconfiguration that adds latency, followed by negative reviews mentioning lag. A government shutdown shifting review volumes overnight.

Internet-routing side (10 features): live anomaly detection, telling on-purpose attacks apart from accidental misconfigurations, “personality profiles” for major networks (some are stable, some are chatty, some are weird), an “internet weather radar” showing where the instability is right now, time-travel replay of past outages, and a tracker for IP-address ranges that announce themselves but don’t actually carry traffic (“prefix ghosts”).

Steam side (11 features): a game similarity engine based on what players actually do in-game rather than the tags publishers attach, a sentiment drift visualizer (is opinion changing over time?), a review-bomb detector that catches coordinated negative reviews, patch-impact maps showing how each update changes the player base, player-migration patterns between similar games, a life-cycle “autopsy” that narrates how a game rose and fell, and review-style fingerprinting that matches similar reviewers across games.

Under the hood: A specialized time-series database (TimescaleDB) for chronological data, a document database (MongoDB) for everything else, public internet-routing feeds, a live dashboard, an HTTP API, basic natural-language analysis on reviews, and geographic mapping. On first run it goes back four weeks for routing data and 60 days for Steam, then catches up automatically after any downtime.

Why it’s different: Nobody builds this. Internet-routing analysis and Steam analytics exist separately — tying them together to detect how infrastructure events affect gaming populations is an original angle. The research framing (network “personality profiles,” prefix ghosts, review fingerprinting) goes well beyond dashboards into actual pattern hunting.

Halfax KeySecrets my own family password manager

A self-hosted password manager I built for me, my family, and a couple of close friends — like 1Password or Bitwarden, but running on my own server so I’m not trusting a third party with my passwords. Each user has their own account and their own master password. The server never sees passwords in readable form — only encrypted scrambled blobs. Even if a hacker got full access to the database, they’d see ciphertext and nothing more.

Sharing is what most password managers get wrong. When I share a Wi-Fi password with my wife, the server doesn’t copy the password — it copies a small encrypted “key” that only her account can unlock. If I want to revoke her access later, I delete that one little key and we’re done — no need to change the underlying password, no chance of leaks. Same goes for any secret. There’s also a forward-looking mode that uses cryptography designed to resist future quantum computers, in case those become a real threat.

Modern, conservative cryptography under the hood. Master passwords are stretched through a memory-hard hash function (Argon2id, the current industry recommendation), so even an attacker with a fancy GPU can’t brute-force them quickly. Everything else is encrypted with ChaCha20-Poly1305 (a current-best authenticated cipher). Master passwords are never stored anywhere — they only exist briefly in memory while you’re logged in.

How it’s served. A small Python web service running behind a production-grade HTTPS server. Plain unencrypted access is refused outright — HTTPS only, no exceptions. The service runs as a tightly-restricted background process with its database credentials stored in a root-only file (so they don’t leak into log files or process listings). The database itself (MongoDB) only ever holds encrypted data.

Login security. Master password + optional six-digit code from any standard authenticator app (Google Authenticator, Authy, etc.) for two-factor login. Even the 2FA secret is encrypted on disk so a stolen database can’t generate working codes. Wrong-password attempts are rate-limited. Every login, share, and registration is recorded in an audit log.

Three ways to use it. A clean web interface in any browser. A command-line tool for scripts. A documented HTTP API for any other program that wants to fetch secrets. It can store seven kinds of items — logins, API keys, SSH keys, free-form notes, certificates, payment cards, and a custom type for anything else — each with appropriate fields, all encrypted.

Why it’s a good project: the design started by thinking about who could attack it and from what angle, not by picking a tutorial and following it. The right modern cryptographic building blocks, real per-recipient sharing instead of just dumping shared passwords in a folder, a future-quantum on-ramp, and the boring-but-essential deployment details most homelab projects skip — production-grade web server, HTTPS-only, two-factor auth, rate limiting, audit logs, no credentials in obvious places.

Halcity city builder — Python + Pygame

A full-featured city builder with a 150×100 procedural terrain world (grass, forest, water). 16 building types, each with subtypes: 5 power plants (Coal, Gas, Nuclear, Solar, Wind), 3 residential (House, Apartment, Villa), 3 commercial (Shop, Office, Mall), 3 industrial (Factory, Warehouse, Tech Lab), and 3 farm variants (Crop, Orchard, Ranch). Buildings must connect to roads to function — roads auto-tile with smart joins (straight, corner, T-junction, crossroad).

The underground layer (Tab toggle) lets you lay water pipes and sewer pipes with a 4-tile Manhattan coverage radius. Water pumps near water tiles produce +15 supply; sewage plants process waste. Both systems affect happiness and pollution.

Turn-based economy simulates population, jobs, food, energy, money, pollution, happiness, water, and sewage every End Turn. Threshold events fire automatically (smog alerts, trade booms, festivals). A prestige system lets you spend points on city decrees (Golden Harvest, Civic Vision, Clean Future). 48×48 pixel-art sprites for every building variant. Cursor-anchored zoom, right-click pan, hover tooltips, and full save/load.

Evolved from a 45,000-line Tkinter prototype into a clean 6-module Pygame architecture: game.py (main loop + world gen), renderer.py (map + UI), game_logic.py (economy + events), sprites.py (pixel art), constants.py (data), ui.py (widgets).

Why it's a good project: City builders look simple but the economy simulation underneath is a real systems problem — interconnected resources with feedback loops, threshold events, and cascading failures. This one models population, jobs, food, energy, money, pollution, happiness, water, and sewage as a coupled system, not independent counters.

Roguelike Dungeon Crawlers 4 iterations — mybad → newmybad

A roguelike dungeon crawler that evolved through four major iterations, each building on the last:

Version UI Size Key Addition
mybad PyQt6 GUI ~107k First playable: dungeon gen, combat, inventory, town, save/load
cmdmybad Terminal / curses ~97k Stripped to pure CLI; same engine, keyboard-only input
myband Terminal ~3k CSV-driven item/monster data experiment (Angband-inspired)

newmybad is the current version. It adds a magic system, expanded combat (13k fight.py), a resource loader with JSON data files for weapons, armor, potions, scrolls, wands, jewelry, and monsters, and a full autonomous AI agent:

The Borg AI (borglib.py 61k + borg_policy.py 80k) plays the game autonomously using a goal-stack architecture (LIFO priorities + FIFO deferred goals), BFS pathfinding, stuck/oscillation detection and recovery, and priority-weighted targeting (monsters 40, stairs 30, healing 25, items 20, equip 15, explore 5). Every step is recorded by borg_instrument.py as JSONL telemetry for post-mortem analysis. A partial Godot 4 port exists in godot_version/.

Why it's different: Four iterations of the same game is the interesting part — each one rebuilt to fix what the last got wrong. The final version has a fully autonomous AI player (Borg) with goal-stack planning, oscillation detection, and JSONL telemetry for post-mortem analysis. That's not gameplay modding; it's building an AI agent from scratch.

Skyhaven RPG browser RPG + Godot 4 port

A Skyrim-inspired browser RPG built in pure HTML, CSS, and JavaScript — no frameworks, no build tools. Full character creation with 10 playable races (Nord, Imperial, Dark Elf, High Elf, Wood Elf, Khajiit, Argonian, Orc, Breton, Redguard) and 5 classes (Warrior, Mage, Thief, Ranger, Paladin), each with unique stat bonuses and starting gear.

Turn-based combat (attack, magic, defend, potion, flee), 12 skills across combat/magic/stealth trees, quest log with multi-stage quests, equipment slots, HP/MP/SP resource bars, level-up with attribute point allocation, NPC dialogue trees, world map navigation, and a full save system.

A parallel Godot 4 port is in progress with GDScript reimplementations of the game data, state management, and core scenes (main menu, character creation, game world).

Why it's a good project: Building an RPG with 10 races, 5 classes, and interlocking systems (combat, skills, quests, dialogue, inventory, progression) in vanilla HTML/CSS/JS — no React, no engine — forces you to manage all the state and rendering yourself. The Godot port proves the design transfers to a real game engine.
