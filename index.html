Virtualization & Orchestration Stack

This environment uses a mixed platform strategy so each workload runs on the right abstraction level: containers for portability, orchestration for multi-service systems, and VMs for full OS isolation.

Docker container runtime

  • Supports fast deployment of web apps, APIs, tools, and utility services.
  • How: Images package dependencies once, then run consistently across hosts.
  • Why: Speeds iteration, simplifies updates, and reduces environment drift.
  • Best fit: Stateless apps, service wrappers, scheduled workers, and edge utilities.

Kubernetes (k3d) orchestration layer

  • Supports multi-service systems with scaling, restart logic, and service routing.
  • How: Declarative manifests define desired state; controller loops keep workloads healthy.
  • Why: Better reliability and lifecycle control for complex project stacks.
  • Best fit: Story systems, API groups, and services needing rolling updates and ingress.

Hyper-V windows virtualization

  • Supports full guest operating systems on the Windows workstation.
  • How: Native hypervisor integration provides virtual switching, isolation, and snapshots/checkpoints.
  • Why: Safe testing for OS-level changes without risking the primary host setup.
  • Best fit: Windows-native lab scenarios, network simulation, and system behavior testing.

VMware Workstation cross-os VM lab

  • Supports parallel Linux VM environments for toolchains and integration tests.
  • How: Snapshot-driven workflows enable quick rollback and repeatable test states.
  • Why: Great for controlled experiments, compatibility validation, and sandboxing.
  • Best fit: Multi-node simulations, distro comparisons, and pre-deployment verification.

Network Stack

The network layer is built around private service discovery, encrypted cross-host transport, and clear role boundaries between local hardware and cloud nodes.

BIND9 Implementation private DNS authority

  • BIND9 serves as the authoritative resolver for my private lab zone.
  • How: Internal records map service names to private endpoints for predictable routing.
  • Why: Stable hostnames let projects move between nodes without rewriting app configs.
  • Result: Cleaner operations, easier service migrations, and less hardcoded addressing.

NetBird VPN Usage wireguard mesh overlay

  • NetBird provides encrypted peer-to-peer connectivity between home lab nodes and VPS hosts.
  • How: A mesh overlay makes each machine reachable as if on one secure private fabric.
  • Why: Services can communicate directly without exposing internal APIs to the public internet.
  • Result: Safe cross-site traffic for orchestration, data sync, and service-to-service requests.

Hardware Interaction Model right workload, right node

  • Betelgeuse handles heavy compute, model inference, and orchestration.
  • UYScuti focuses on development, game builds, and workstation-class experiments.
  • hera-pi runs lightweight utility services and always-on support tasks.
  • Cloud hosts provide public entry points while private internals stay on the mesh.

How It Supports Projects design rationale

  • Named DNS services + mesh routing make multi-node projects composable and maintainable.
  • Container and VM platforms can consume the same internal network conventions.
  • Public and private planes stay separated: internet-facing UX, private backend control paths.
  • This architecture supports AI apps, story systems, monitoring tools, and game services together.

Let's Encrypt TLS automated certificate authority

  • Every public-facing service uses free TLS certificates from Let's Encrypt (ISRG).
  • How: certbot handles issuance and renewal via ACME v2 with zero downtime (Apache plugin for web, standalone for mail).
  • Coverage: www.guywithgames.com, www.guywithbeer.net, mail.guywithgames.com (SMTP/IMAP), www.shopmom.net — all ECDSA.
  • Why: HTTPS for everyone, no cost, no friction. Auto-renews 30 days before expiry via systemd timers.

Let's Encrypt is a service everyone on the internet benefits from. Consider donating to ISRG to keep it free.

AI & Story

Story Universe Ecosystem a fictional world that writes itself

A fictional world that generates its own stories around the clock, spread across three computers in the homelab. A Chronicle Keeper (Raspberry Pi) holds the master record of every character, location, and past event, and broadcasts a world clock. A Narrative Engine (main server) listens for those ticks and uses the Halfax AI server to generate each new event. A World Browser (cloud host) shows the live chronicle as a public web page anyone can watch.

It actually remembers. Every accepted event is written into MemPalace, a long-term memory store. Before generating the next event, the engine searches MemPalace for related past events and feeds them in as background, so the AI builds on continuity instead of contradicting itself. A quality filter rejects clichéd openings and time-of-day contradictions, then feeds the rejection reasons back into the next attempt as live counter-examples.

If something breaks, the world pauses — it never lies. A health monitor checks every dependency each tick. If the AI server is down, the universe stops generating and waits silently until service returns. No fake fallback, no hallucinated events.

Why it’s different: Most AI story generators are one-shot — prompt in, text out. This is a persistent, multi-machine world with a single source of truth, real long-term memory, self-pausing dependency handling, and a measurable prose-quality feedback loop. The architecture is closer to a game backend than a chatbot.

Halfax AI Stack my own AI server, running at home

My personal AI “brain” running on my own hardware. Three models serve in parallel on one GPU — one for code (Qwen3-Coder), one for story-writing and reasoning (Dark Champion), one general-purpose (Mistral) — with a watchdog that auto-restarts any crash. The API speaks the standard OpenAI dialect, so any tool built for ChatGPT (editors, chatbots, scripts) plugs in unchanged.

Three kinds of memory wrapped around it. A 99,000-chunk knowledge library of my PDFs, offline encyclopedias, and notes — relevant pages get pulled in automatically when I ask questions. MemPalace, a long-term memory store the Story Universe writes every event into so narratives stay consistent across days. And a personal memory layer with rules, identity facts, and preferences I’ve told it — loaded into every chat the way ChatGPT’s memory works, except every byte lives on my disk in plain text I can read.

The model literally can’t produce broken JSON. When I need structured data back, the server hands the model a strict template that blocks the model, letter by letter, from typing anything that would break the format. Combined with the rest of the stack, this is the difference between an AI that “usually” gives valid output and one that “always” does.

Why it’s different: Not a wrapper around someone else’s cloud. Three models, three layers of memory, automatic failover, self-healing watchdog, guaranteed-valid structured output — all on my own hardware. No monthly fee, no tokens billed, no data leaving the network.

Halfax AI VSCode Extension my own AI assistant inside the editor

My own coding assistant inside VSCode — same role as GitHub Copilot, Cursor, or Claude Code, but running entirely against my own AI server. Chat sidebar, autonomous agent mode, type-ahead autocomplete, one-click apply on suggested edits, Cmd+K inline rewrites on any selection.

Agent that works on its own — transparently. Hand it a task like “read the README and fix the broken test” and it loops: think, call a tool, read the result, decide the next step. Every tool call shows up as an inline card with its arguments before it runs — I approve once, approve always, or refuse. After three errors in a row it pauses and asks me what to do instead of spinning. State is visible at every step.

It remembers, and the memory is mine. Every chat and agent run auto-saves to a JSON file in my home directory and auto-resumes when I reopen VSCode — even after a crash. Personal memory works like Claude Code’s skills and memory: rules I’ve told it, identity facts, and preferences load into every conversation. Custom slash commands are just markdown files I drop into ~/.halfax/skills/. Lifecycle hooks let me run shell commands on session start, tool call, or agent stop. Everything configurable is a plain text file I edit, not a vendor settings UI.

How it differs from Claude Code, Windsurf, and GitHub Copilot. Those all send every keystroke and chat to a corporate cloud, require an account, run telemetry, bill per token or seat, and stop working without internet. Mine runs locally end-to-end — works offline, never phones home, no token meter, no rate limits. The agent state machine is visible and pauseable; every destructive tool call hits a permission prompt by default. Self-updates pull from my homelab, not a marketplace.

Why it’s a good project: The full IDE assistant surface — chat, agent, autocomplete, inline edits, sessions, skills, hooks, persistent memory, self-update — without a byte leaving the box. A complete self-hosted parallel of an entire commercial ecosystem.

This server is the bridge between the AI and all five machines in my homelab, using MCP (Model Context Protocol) — the same open standard Claude Code uses to access tools. Checks 35+ services across 5 hosts in under 2 seconds.

Local + remote in one surface. On my main server: services, Docker containers, AI model response times, GPU temp/power/memory, DNS, VPN mesh, Kubernetes, the Story Universe engine. Remote (Linux + Windows): list services, pull logs, check disk/memory, run arbitrary commands with a destructive-pattern blocklist, transfer files, stream logs. Dedicated workflows for the Story Universe (status, log analysis, full reset-the-world) and site deploy (this page was edited locally and pushed live through these tools).

Why it’s a good project: Most MCP examples online are toy demos. This one runs against a real mixed fleet — Linux and Windows, local and remote, containers and bare metal — with actual safety controls. Plain-English requests become structured queries the AI can act on across the entire homelab.

Halfax System Reporter deep-dive hardware monitor

Tells me everything about a machine’s hardware — per-core CPU temperatures and wattage, exact memory timings, SSD wear, GPU details, battery health, display info — all in one window. Most of that information lives behind privileged OS layers normal apps can’t touch, so I wrote my own Windows kernel driver that loads into the deepest layer of the operating system and reads sensors directly. Same approach commercial tools like HWiNFO use, written from scratch.

Multi-layer fallback per subsystem — if the kernel-driver method fails, the app tries Windows’ built-in APIs, then a third method, before giving up. A 5,500-line graphical interface organizes CPU/memory/storage/network/GPU/battery into tabs. The same app runs on Windows (kernel driver), Linux (sysfs), and Raspberry Pi (device-tree).

Why it’s different: Most system monitors only show what Windows is willing to reveal. Writing a kernel driver that loads into the most-privileged layer of the OS is a fundamentally different level of work than calling an API.

Systems & Security

HalfaxOS a real operating system, written from nothing

A complete 64-bit operating system written entirely from scratch — no Linux, no BSD, no borrowed code. About 413,000 lines of original C and Assembly. Boots on real hardware and in virtual machines.

Built around “permissions can only shrink, never grow.” Most operating systems use a 1970s permissions model. HalfaxOS uses capability-based security: programs hold typed permission tickets, and handing a ticket can only reduce what the receiver can do, never grant more than the sender had. This makes whole classes of security bugs structurally impossible — the same direction Google’s Fuchsia OS and ARM’s CHERI architecture are heading.

It’s a working OS, not a demo. Multi-core scheduler, virtual memory, message- passing between programs, a from-scratch TCP/IP stack that actually browses the internet, an Intel network card driver, a graphical window manager with draggable windows and a taskbar, multiple filesystems including exFAT. 38 system services (Linux has 450+) — small and focused on purpose.

Why it’s different: Not a hello-world bootloader someone called an OS. A real security thesis built on shrink-only permissions, plus a full networking stack, window manager, and CPU-enforced user-program isolation. A working operating system built from nothing.

ComboServer do internet outages hurt video-game sales?

A research-style platform asking a question nobody else has built tools for: do internet routing problems actually affect gaming? It watches the live “road map” of the internet and Steam at the same time, looking for real correlations — an outage in one country followed by a player drop in that region, a network misconfiguration followed by reviews mentioning lag.

21 analyses across both sides. On the routing side: live anomaly detection, attacks-vs-misconfiguration classification, “personality profiles” for major networks, a real-time instability map. On the Steam side: a player-behavior-based game similarity engine, sentiment drift, review-bomb detection, patch-impact maps, player migration between similar games, review-style fingerprinting.

Why it’s different: Internet-routing analysis and Steam analytics exist separately — tying them together to detect how infrastructure events affect gaming populations is an original angle. The framing goes well beyond dashboards into actual pattern hunting.

Halfax KeySecrets my own family password manager

A self-hosted password manager for me, my family, and close friends — like 1Password or Bitwarden, but running on my own server. Each user has their own account and master password. The server only ever sees encrypted blobs — even with full database access, an admin can’t read anyone’s passwords.

Sharing is what most password managers get wrong. When I share a Wi-Fi password with my wife, the server doesn’t copy it — it seals a small key that only her account can unlock. Revoking access later is just deleting that one key — no rotation, no leakage. There’s also a forward-looking mode that uses cryptography designed to resist future quantum computers.

HTTPS-only, modern crypto (Argon2id for password hashing, ChaCha20-Poly1305 for everything else), optional two-factor login from any standard authenticator app, rate-limiting on failed logins, and a full audit log of every login / share / registration. Three interfaces: a web UI, a command-line tool, and a documented HTTP API.

Why it’s a good project: the design started from a threat model. Right modern crypto, real per-recipient sharing instead of dumping shared passwords in a folder, a future-quantum on-ramp, and the boring-but-essential deployment hygiene most homelab projects skip.

Games

Halcity city builder — Python + Pygame

A full-featured city builder with a 150×100 procedural terrain world (grass, forest, water). 16 building types, each with subtypes: 5 power plants (Coal, Gas, Nuclear, Solar, Wind), 3 residential (House, Apartment, Villa), 3 commercial (Shop, Office, Mall), 3 industrial (Factory, Warehouse, Tech Lab), and 3 farm variants (Crop, Orchard, Ranch). Buildings must connect to roads to function — roads auto-tile with smart joins (straight, corner, T-junction, crossroad).

The underground layer (Tab toggle) lets you lay water pipes and sewer pipes with a 4-tile Manhattan coverage radius. Water pumps near water tiles produce +15 supply; sewage plants process waste. Both systems affect happiness and pollution.

Turn-based economy simulates population, jobs, food, energy, money, pollution, happiness, water, and sewage every End Turn. Threshold events fire automatically (smog alerts, trade booms, festivals). A prestige system lets you spend points on city decrees (Golden Harvest, Civic Vision, Clean Future). 48×48 pixel-art sprites for every building variant. Cursor-anchored zoom, right-click pan, hover tooltips, and full save/load.

Evolved from a 45,000-line Tkinter prototype into a clean 6-module Pygame architecture: game.py (main loop + world gen), renderer.py (map + UI), game_logic.py (economy + events), sprites.py (pixel art), constants.py (data), ui.py (widgets).

Why it's a good project: City builders look simple but the economy simulation underneath is a real systems problem — interconnected resources with feedback loops, threshold events, and cascading failures. This one models population, jobs, food, energy, money, pollution, happiness, water, and sewage as a coupled system, not independent counters.
